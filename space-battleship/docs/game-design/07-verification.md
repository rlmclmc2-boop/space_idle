# 07 验证与实施切片

[回唯一入口](README.md)。本次交付仅文档，未运行Godot游戏测试。以下定义未来重写的验证体系，不能把尚未执行的测试写成通过。

## 1. 一套规则，一种场景运行器

生产Excel和测试Excel通过同一个ConfigCompiler生成相同ConfigBundle；测试不复制生产表、不在用例代码中构造一套隐藏平衡数据。测试工作簿显式提供所需最小定义，允许专门小数值以便手算，但必须经过同一类型/引用/拓扑校验。每个测试数据包自足，不能运行时从正式大表补缺失行。

`tests/excel/`规划分包：`core_rules.xlsx`（最小资源/装备/关卡/敌人）、`combat_cases.xlsx`、`progression_cases.xlsx`、`hyperspace_cases.xlsx`、`persistence_cases.xlsx`。这些为测试独立权威；schema与生产共享，内容完全独立。不要求本次文档任务创建这些xlsx。

测试用例表：

| 表 | 列与含义 |
|---|---|
| case | case_id、config_fixture、seed、duration、executor、comparison_mode |
| initial | case_id、entity_kind、entity_id、field_id、typed_value；field_id从测试装配允许表，不任意执行路径 |
| commands | case_id、sequence、at_game_time、command_kind、typed_args |
| clock_segments | case_id、order、real_dt、focus、pause_action、speed；专项测试现实/游戏转换 |
| expected_state | case_id、checkpoint、owner、field_id、value、tolerance_kind、tolerance |
| expected_events | case_id、sequence、type、source_id、target_id、amount、count |
| expected_errors | case_id、operation、reason、must_leave_unchanged |
| fault_schedule | case_id、adapter、boundary、fault_kind；仅注入IO/执行器交接错误 |

运行器做四件事：编译fixture；建立GameSession与替身Clock/Random/FileStore；按计划发送真实命令并推进真实规则；比较状态与回执。失败输出首个分歧时间、规则ID、来源Excel坐标、相关输入与期望，不复制整个玩家档。无SceneTree的领域用例仍可用Godot headless运行；配置编译器可单独用Python测。

期望值不能调用生产公式生成，否则只是自证。可手算例子写在Excel；复杂随机效果用固定随机序列、明确抽样槽或独立统计区间测试，不硬编码“第42次randf”的偶然顺序。常规测试只用小矩阵；新增规则才添加对应边界，避免每次文档改动跑整游戏。

## 3. 配置负例与覆盖

独立负例工作簿至少包括：重复ID、缺外键、关卡战点越界/乱序、非法概率、空必填、文本伪数字、公式缺缓存、非法sheet、科技环、星球解锁环、重复槽索引、尺寸包络重叠/越界、路线未覆盖/重复组、预算块重复/缺失、零预算被压缩、词缀区间反转、传说值同时不在当前/历史两区间、未知规则键、生产/测试manifest交叉引用。

编译失败必须给到单元格和稳定错误码，active包hash不变。编译全部正式Excel一次验证实际内容完整，但不把正式平衡当成每个单元测试的隐式依赖。内容回归比较ID集合、有效行数、关键字段、引用和语义hash；候选表/发布副本不得覆盖根表。

## 4. 执行器合同与性能

参考执行器是新规则的可读实现，native是同合同后端。对同fixture、同seed、同命令、同初始快照比较：命中顺序/目标/计数、死亡唯一性、费用与掉落、状态机、残余时间、所有随机流末态。Amount在约定容差内，身份与事件数必须完全相同。不同渲染帧分块、native→reference→native切换不得改变这些结果。

大数native不支持时明确选择reference，不把大数钳成最大double。不能以“速度快”为理由跳过某个传说/分支。比较只覆盖后端宣称支持的能力集；未支持不应报告通过。

性能场景为15槽敌群、最大启用普通槽+无人机、连发连锁/光束、长时间10倍、满仓和高额MAX。记录平均/高分位步耗时、最大队列长度、每步分配数、待执行时间、渲染耗时分别统计。目标预算先在目标硬件基线实测后定，不捏造“已达60fps”。技术预算耗尽保留待执行时间与候选事务，下一帧续做；不把演出对象数量限制变成攻击数量限制。

## 5. 可审阅实施切片

本表是用户批准后的实施顺序，不是本次编码计划已开始。每切片保持可运行的小闭环，不写临时两套长期业务来绕过重构。

1. **配置与数值**：独立编译器、schema、Amount、测试Excel、配置负例。完成后可在无Godot环境编译内容，所有新业务只能读Bundle；D01/D04等未决内容以明确未启用分支阻止发布。
2. **最小自动战斗**：新会话、装备/钱包、航行、4武器、敌盾甲、命中/死亡/拾取；接静态/纯表现资产。通过C01～C08/E01/T01，再进入强化。
3. **完整战斗成长**：强化六效果与分支、反应炉、AI、换装/属性重投影、统计。通过相关组合和数值边界；只实现已决定规则。
4. **船员/星球/星系**：统一占用、探索、施工、经验、收益和重铸候选。验证跨域事务和时间分块等价。
5. **超空间闭环**：独立编组/奖励绑定、手动返回、挂机凭据、无人机仓库/改造/挂设/传说/过滤/预设。完成所有H场景，再接完整UI。
6. **存档与运行恢复**：新Envelope、串行writer、导入/备份/失败恢复，D10后实现选定的战斗续局合同。不得等发布前才补保存一致性。
7. **native/GPU与性能**：适配旧快路径到新协议，通过差分再启用。先保留正确reference可回退；表现与业务性能分开评估。
8. **收口**：替换主场景装配、移除旧业务与旧测试、删除游戏依赖编辑器入口，保留经审查的资产/表现和独立编译/测试命令。全量正式配置导入与有限玩家流程烟测。

第6项的保存骨架应在第1项建立，后续每域随加入扩展schema；编号表示完整验收点，不代表前五阶段不保存。每切片的代码、测试Excel、运行器与文档同分支提交。用户审阅方案后才能安排实施，不能将文档分支直接当作游戏发布。
