# 太空战舰：新游戏运行架构方案

本方案从 `main` 的实际游戏代码和 Excel 配置重新建立需求，再据此设计实现结构。基线为 `b4729b9a9803458b5ac19a4945c2fe0d5f76e51f`。本方案已纳入用户确定的玩法选择；此次只更新设计，尚未实施游戏代码。唯一交付入口是本页；下列正文共同构成方案，实现者不需要旧方案或聊天记录。旧重写方案未用作输入。

## 1. 游戏怎样工作

玩家驾驶一艘自动作战的飞船，沿关卡距离前进；到达战点后停留交战，消灭编队，收取铁、铀和强化碎片，继续前进或驻守重复作战。各武器按自身命中规则结算伤害：我方普通炮与Higgs在发射调用内即时命中，飞行弹体在实际接触时命中，持续光束在有效伤害跳到期时命中。命中才改变目标的生命、防御、受击效果和死亡状态。舰体显示位置与命中几何来自同一个逻辑战场，画面帧率不决定伤害。

玩家只有在当前护盾与当前装甲均耗尽时才进入死亡/重建判定；任一类仍有当前余量就继续存活。首模块防御槽不可为空，但可选择合法防御类型，不固定为复合装甲；仅无装甲不能作为死亡、撤退或拒绝出击的条件。当前余量与装备提供的最大容量是不同数值，详见[01流程](01-runtime.md)、[02承伤](02-combat.md)与[03槽位](03-progression.md)。

顶部定时资源在生成时确定最终数量；之后研究等倍率变化只影响新生成的物，已有物移动及领取均不重算。此规则只适用于定时物，详见[01经济](01-runtime.md)与[07验收](07-verification.md)。

铁购买槽位等级，铀购买反应炉等级，强化碎片购买全局强化。槽位等级属于槽位，换装备保留等级；船型决定当前启用几个槽位。反应炉把能源分配给武器、防御、炼铁和碎片凝聚。AI 科技消耗研究工作量，可持续投入铁和铀加速；船员可以自动购买、自动续研，也能探索星球和星系。星球探索、建筑和重铸形成跨轮成长；星系的建设和资源收益形成另一条长期进度。超空间有四条武器路线，手动挑战建立层数和最佳时间，在线挂机按最佳时间生成无人机及材料；无人机提供额外武器、词缀、挂设和传说效果。

所有这些系统共享一份经济账本和一条游戏时间线。系统函数直接按固定顺序协作：有费用的动作先检查全部费用和引用，再更新相关数据，函数完成后界面才读取。例如星球探索完成会同时增加探索度、推进施工、发放船员经验、重新计算装备和反应炉上限；任何观察者只能看见这一整次结算前或结算后的状态。

## 2. 已确定边界

| 范围 | 本方案约束 |
|---|---|
| 重写 | 业务代码与测试重写；不照搬原有管理器关系、存档对象和测试脚手架 |
| 实现基础 | 战斗以现有native/GPU快路径为基础，补齐完整玩法；静态资产和纯表现可复用 |
| 战斗 | 命中时结算伤害；我方炮即时命中，其余按各自接触/周期规则，不预扣未来伤害 |
| 数值 | 统一近似大数；极端 MAX 允许数量级近似，不建两套普通/大数经济系统 |
| 配置 | Excel 是唯一权威入口；保留配置内容；应配置的硬编码纳入 Excel；已删除成长配置保持删除 |
| 测试 | 测试数据使用独立 Excel，经同一编译器进入同一业务实现 |
| 存档 | 不要求旧存档连续性；设计新的清晰版本和恢复协议 |
| 编辑器 | 删除依赖游戏运行的编辑器；不安排编辑器开发。命令行配置编译和测试运行器不属于游戏内编辑器 |
| 变更权限 | 不自行决定玩法歧义，不将建议变更混入确定规则；仅设计，用户审阅后才实施 |

“保留配置内容”不意味着把已停用功能重新开启。旧科研、未消费配置字段、候选编组和发布副本有明确分类。现存装备进化保留并迁入Excel；其他已删除成长配置保持删除。已定玩法与目标Excel字段见09，基线表值仍单独保留为来源事实。

## 4. 核心结构及其必要性

`GameSession`是一个小型主线程入口，持有航程、钱包/收入、装备与反应炉、强化、科研、船员、星球、星系、超空间、通知和时间数据。各系统文件提供具名函数，直接读写这些数据。玩家点击升级就调用购买函数；函数先查全部条件，再扣费、升级、更新战斗配置，返回后界面才刷新。帧入口按01定义的共享顺序逐个调用系统，不靠事件广播驱动业务。

实时战斗始终由现有`SpaceCombatKernel`扩展后的C++核执行。核独占盾甲、弹体/光束、冷却、强化暂态、传说效果、战斗随机和攻击/来袭历史；Godot保存长期成长，提供编队、装备数值与逻辑几何。每次推进后Godot一次取走已发生的掉落和波结果，直接处理拾取、通关、超空间奖励和航程。这个分工让每帧大量接触继续走现有native路径，也让奖励与长期成长仍由少量清楚的顺序函数完成。

现有native并未覆盖全部玩法：新设计明确把缺失的强化分支、五种传说、手动超空间和连续波次加入同一核，详见05；不另建一套GDScript战斗。`SpaceCombatPresentation`和GPU读取核的紧凑表现数据，绘制不会改变命中结果。统一Amount算术在C++实现并提供Godot绑定，普通与大数都走它；离散计数使用整数，伤害不先转普通浮点。

独立对象只保留实际需要者：ConfigBundle提供Excel编译数据，SaveFiles管理异步磁盘文件，页面脚本负责输入和显示。测试Excel经同一编译器，由headless Godot驱动同一个GameSession与native核；几何和Amount纯函数可直接测试。无需为了测试再实现一次伤害规则。

## 5. 一次完整操作示例

玩家在战斗中把武器槽从19级买到20级：页面调用`session.buy_levels(slot_id,1)`；装备函数检查槽位、门槛、钱包和材料，计算新等级对应数值并检查native可接收的配置。本次跨入第一进化阶，额外支付10简并物质并获得1.6进化倍率；材料未开放或余额不足时拒绝购买。

检查通过后，同一主线程调用中依次扣费、写等级、重算装备、更新核的后续攻击参数，再返回显示结果。已经飞行的弹体保留出生数值。购买防御等级时按03增加新旧容量差；换装、科研、强化等各按该章明确的防御调整规则。下一次战斗推进按对应武器的即时命中、飞行接触或周期跳结算伤害；产生的掉落取回宿主列表，领取才入钱包、更新收入峰值和相关属性。每一步谁持有数据、何时改变都由具名调用直接表达。

已定玩法汇总在[08](08-decisions.md)，并直接落实到各章：进化保留、禁止第二代连发、武器无天生暴击而critical主效果提供25%、保底暴击仍保留原率爆伤机会、超空间1层免费且探索至少10秒、星系按平均每秒收入、固定步完成余时舍去、保留目标排序、加载重开战场且导入发微粒、普通价格分批一致，以及盾甲同时耗尽才进入死亡/重建判定。本文只交付设计，用户批准实施后才修改游戏代码。
