项目中的状态还应区分：**持久进度、待结算工作、战斗会话、派生投影、显示状态、配置版本和分析产物**。它们的生命周期不同；当前问题往往发生在这些类别转换时，不能只按所属文件判断。

**按影响范围、故障后果、扩展牵连和维护成本，结构性问题排序如下。**

**1．完整状态变化仍由调用者手工拼接，领域所有权尚未覆盖完整业务提交。**

【事实】`Economy`、装备、船员、星球、科研、超空间等已收拢自身写入，部分读取视图也已冻结。这确实防止了很多任意修改。装备购买、换舰和超空间领奖还已有“准备—复核—共同提交—通知”的良好实现。

但一次成长或配置变化，仍需要协调者分别记住：

- 原生执行能否继续、是否必须交接；
- 钱包和其他域的提交顺序；
- 哪些贡献版本改变；
- 容量、生命、攻击来源和待发攻击如何协调；
- 哪些自动任务需要唤醒；
- 哪些 UI 事件应在何时发布；
- 保存及恢复需要包含哪些状态。

这些责任分别位于 `Game`、三个 runtime、属性依赖列表、船员事件分派和页面事件分派中。**状态有唯一写入者，并不意味着一次变化只有一个完整提交边界。** [属性依赖]( /workspace/space_idle/space-battleship/scripts/attribute_projection.gd:12)、[自动任务事件分派](/workspace/space_idle/space-battleship/scripts/crew_system.gd:112)、[成长提交协调](/workspace/space_idle/space-battleship/scripts/progress_runtime.gd:195)。

【推断】这使新增跨域功能的主要成本成为“找齐受影响的消费者”，容易出现状态已经正确、自动消费或属性仍旧的情况。上一轮的收入口径、失败时丢失本段工作等，只是这种结构的具体表现，不应分别发展成独立补丁工程。

应形成的原则是：**业务命令拥有完整结果；提交结果明确描述变化与完成状态，贡献更新和消费者唤醒从已提交结果产生。** 时间消费者也必须明确“已消费、保留待办或阻塞”，不能仅返回成功／失败而让上层猜测。可以沿现有具体协调器完成，不需要大型通用事务框架。

**2．同一玩法横跨多个执行环境，但支持范围与等价关系没有整体闭合。**

【事实】正式游戏使用 `PresentedBattleGame`，其中有独立的导弹发射、运动、目标和几何行为；F8/F9 使用继承基础 `BattleGame` 的 `BalanceGame`，另有 FAST 调度；原生内核又拥有自己的执行实现。

已经共享的属性投影、掉落计算和攻击出生配置值得保留。原生编译器对不支持的分支、数值域和能力明确拒绝，也是一种有效的预防结构。但它不能自动证明其他执行环境等价：

- `BalanceGame.stat` 仍返回 `float`，部分攻击路径使用普通乘法；正式成长数值则允许 `GrowthNumber` 字典表示。
- Lab 的科研跳过条件仍读取已退役的科学家／旧科技字段。
- Lab 的 `exact` 是其自身执行模式，不是正式战场等价性的证明。

这些是静态接口差异；本轮没有证明它们在所有当前输入下都造成错误，也不要求工具必须实现全部正式战斗能力。[Lab 执行边界](/workspace/space_idle/space-battleship/scripts/balance_game.gd:39)、[批量战斗创建](/workspace/space_idle/space-battleship/scripts/player_loadout_generator.gd:337)、[原生支持范围](/workspace/space_idle/space-battleship/scripts/native_execution_compiler.gd:30)。

【推断】新增武器、加成或数值范围时，开发者仍可能只完成一个环境，另一个环境继续产生看似有效的结果。这会影响数值判断、自动生成关卡和长期回归，范围远大于单次战斗异常。

应形成的原则是：**共享玩法语义，各执行器声明其支持范围；不支持时明确拒绝、降级或标明模型差异。** 新能力不能靠“它继承了 Game”获得等价资格，也不应被迫在所有后端重复实现。

**3．替换、恢复和版本身份的规则分散，尚未覆盖完整产品状态。**

【事实】当前已有不少扎实边界：

- 存档写入锁、临时文件回读、备份及拒绝覆盖坏档；
- 配置导入复核输入及目标快照，回滚失败保留恢复材料；
- 发布使用隔离目录，验证后才发布；
- 原生交接先准备接收状态，再停止旧执行者并绑定新视图。

但这些边界采用不同的完成判据。内存加载、场景重载、导入回滚、重铸启动和多文件配置替换，没有统一回答“何时可恢复消费和写入”。例如存档启动恢复未完成会冻结写入，导入的场景重载失败分支却不以回滚成功作为重新启用写入的条件。配置的 `atomic_batch` 也明确只是可恢复的尽力批处理，不是跨文件原子提交。[存档恢复出口](/workspace/space_idle/space-battleship/scripts/main.gd:1035)、[配置批处理](/workspace/space_idle/space-battleship/tools/config_workbooks.py:51)。

版本身份也存在边界差异：普通游戏读取生成 JSON，独立分析器会重新读取外部敌人 Excel；批次保存数据哈希和引擎版本，发布校验 DLL 哈希及实际准入，但这些信息本身没有把规则源码、数据快照和执行器版本统一关联起来。**未发现当前 DLL 必然过期；这里指出的是现有证据不能证明它与当前源码对应。**

应形成的原则是：**替换以完整状态就绪为成功，恢复以权威来源重新确定为完成；尚未完成时，不恢复普通消费。** 可复用分析结果需要标识实际规则与数据版本，而不是仅标识文件内容或引擎。版本边界应按业务相关性划分，不必把无关美术变化耦合进战斗结果。

**4．重构迁移未覆盖全部受支持消费者，验证和交付清单仍可能停在旧结构。**

这是本轮扩大到项目全貌后发现的直接证据。

【事实】独立分析器清单仍列出已删除的 `hyperspace_battle_return.gd`、`hyperspace_main_return.gd`，同时漏列当前核心直接引用的多个所有者／协调器。其构建入口会检查文件存在和依赖闭合，因此**按当前源码，该构建入口会拒绝现有清单**；本轮没有实际运行构建。[分析器清单](/workspace/space_idle/space-battleship/tools/analyzer_required_data.json:3)、[构建依赖检查](/workspace/space_idle/space-battleship/tools/build_result_analyzer.py:17)。

测试指南仍推荐 `test_state_ownership.gd`，它却直接读写旧 `profile.resources`、`profile.loadout`，并引用已退出的接口。架构文档仍把所有领域状态归于 `profile`，描述旧存档版本和旧科研入口。[当前指南](/workspace/space_idle/test/guides/equipment.md:5)、[旧状态消费者](/workspace/space_idle/test/test_state_ownership.gd:9)。

【推断】这里的根因不是“少改几个文件”，而是**组件退出和接口迁移没有以全部受支持入口为边界结束**。只完成主场景，外围工具、打包、测试和文档仍可能继续消费旧模型。添加更多局部测试无法替代这个边界。

应形成的原则是：组件公开什么能力、谁仍受支持地消费它，必须可定位；接口改变时，这些消费者要么一同迁移，要么明确退出。旧测试名称和历史 `COVERED` 标记不能继续承担当前覆盖证明。

**重新评价历史收益，结论不是全盘否定。**

两个历史提交均已核实存在且为当前祖先。相对 `31e79337`，领域所有者、不可变视图、贡献版本、共享战斗投影和简化超空间返回，降低了正常路径的写入混乱与对象恢复负担。相对 `6a8388c2`，后续六个提交进一步改善成长协调、启动准备、调度时机、几何生命周期和静态描述复用。

但收益主要集中在正式运行主干。静态历史核对显示：`31e79337` 的分析器清单已漏列 `reactor_integer.gd`；到 `6a8388c2` 出现已删除返回脚本和新领域依赖未同步；当前又增加 `progress_runtime.gd` 的遗漏。**整体迁移闭合不足是持续存在、随扩展放大的问题，不是最近六个提交才制造出来，也没有被它们解决。**

用户明确的资源规则仍成立：联合一体化只计合格的战场原生拾取，排除衍生收入，并与星系生产共用权威事实、按用途查询。当前峰值混用总收入窗口是上述权威边界不足的一项证据。时间、倍率和 `auto_gen` 资格仍未定，不能用代码现状补成需求。

**全局收尾应以这些结构证据成立为准，而不是完成下一批修复：**

- 一个新增跨域能力能沿明确的命令、贡献和生命周期边界接入；无需逐处猜测需要清什么缓存、发什么事件、唤醒谁。
- 所有受支持入口对该能力采用同一语义，或明确声明不同模型／不支持；数值域、时间和随机性不靠继承关系暗示。
- 任一提交或替换中断后，都能确定权威状态、剩余工作和恢复条件；恢复不依赖恰好正确的调用顺序。
- 域内读取保持只读，表现和分析消费稳定投影；用于不同用途的查询可以不同，但不能自行重建权威事实。
- 正式场景、工具、打包和有效测试的依赖范围闭合；旧消费者退出后，清单和覆盖声明同步退出。
- 验证围绕稳定业务不变量复用场景，分别证明域内规则、跨域提交、执行器支持范围和真实入口；性能收益按同等工作量验证，维护收益体现为新增功能需掌握的约定减少。

本轮完成的是**覆盖项目全貌的结构审计**，不是逐行算法验证：未运行测试、构建、磁盘故障注入或性能测量，也未穷举战斗组合、素材与 UI。没有权限阻塞。现有证据足以否定“全局结构已收尾”，同时也足以确认现有主干有可继续收敛的基础；尚不足以承诺全项目行为正确或长期性能达标。
