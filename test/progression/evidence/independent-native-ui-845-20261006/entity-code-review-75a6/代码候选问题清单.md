## 可执行问题（父先转实现线程）

**P1：允许调大拆解数，但自动筛除后的奖励仍硬拒每类模块>10。**
`tools/hyperspace_entities.py:191–192`仅验证dismantle_amount≥1；GodotConfig.valid也没有上界。纯投影将legendary=51合法接受；Rewards.dismantle固定随机分配51份到5模块，因此至少一模块≥11，无需依赖随机种子。system.complete自动筛除生成机后调用State.valid_reward，而 `hyperspace_state.gd:27`固定每key≤10，必定invalid_reward，探索不能完成冻结/领取。直接dismantle可能成功，形成操作路径差异。
最小修复选择：将valid_reward上界跟配置最大拆解数量联动（保持当前默认结果，验证整数/总量边界）；或将表/导入/启动统一限制≤10并如实标硬限制。契约“奖励校验上界联动”目前未实现。短验收：legendary51/全筛除，结果稳定可结算，或在导入阶段明确拒绝，不能运行才拒。

**P2：合法量化单点被浮点误差拒绝。**
Pythonvalidate_config:201及Godotquantized_range用无容差ceil(low/precision)≤floor(high/precision)。实测纯投影global_damage T5=[0.043,0.043]、precision=.001被拒；商是42.99999999999999，ceil43>floor42。实际Rewards.R.quantized已使用±1e−7，得到low=high=43，是合法网格点。需共享与抽取相同的网格边界容差，导入/启动/随机取值三者一致；不要人为禁止策划精确单点区间。

**P2：可编辑标记仍与固定身份矛盾，槽位移动并未实现。**
Schema编队槽位slot_index、成员分配slot_index、改造费用resource列标editable=true；前两者同时被locked，后者为固定primary_key(resource)，都不会被映射为新结构。纯投影槽0→当前空槽2立即immutable identity/structure mismatch；这不仅是UI保护问题。若本轮保留槽结构/预算成员数，请将这些列标只读并说明；若要求支持合法搬位，需要用稳定member_order/rowID识别，再重建15槽null/positions/recipe.slot，不能仅改editable文案。当前模板锁了非空槽集合，因此支持的是坐标移动及既有槽enemy替换。

- 所有modernization_tier_weights=0被要求sum>0拒绝，但合同各附加系数允许非负；modernization_base_coefficient>0仍保证正基础费用，公式无需附加权重sum>0。建议放开或明确锁定这一组合，避免两端文案矛盾。
