# Single-slot structure acceptance, 2026-10-16

Base: `d2f5db1aa4b8b10e563456bde03eaf337635ccf3`. Candidate branch: `feat/single-slot-first-three-20261016`. This phase changes ship capacity, physical mounts and player survival. It does not rebalance weapon, reactor or enemy values.

`ship.xlsx` is the capacity authority. Its five rows project through `import_workbook.read_rows`, `convert_sheet`, `validate_projection` and `encode` into `game_data.json`: weapons `1/2/3/4/5`, defence `1/1/2/2/3`. The normal incremental wrapper could not start because the local Python environment lacks `lxml`; the same repository importer functions generated and validated only the ship projection. The second hull unlocks after level 10 clear, so the first three levels use the one-slot Frigate without changing unlock thresholds.

The old "drone" was a visual carrier for weapon slots that exceeded a hull's authored mount budget. `hybrid_layout.assign` now requires a physical mount per active weapon and never assigns a carrier. This does not remove hyperspace drones: their inventory, reward binding, combat source, shared effects, chains and DPS remain in place. The five PNGs here are actual Godot renders with every slot equipped with a level-1 laser. [visual.log](visual.log) records `weapons=physical=1..5` and `carriers=0`. The two-dimensional hardpoints, three-dimensional GLB mount nodes, hybrid manifest and panel preview mount counts match for every hull. Existing hull geometry contains no installed weapons; four unused mount nodes were removed from the first three GLBs.

Short isolated tests use `BattleGame.new(..., false)` or a new `SpaceCombatKernel`; they read no player save.
