# 整体性能优化：32991cc 基线

已修复三个实测热点：装备 MAX 重复报价、保护层 HUD 重复投影、正交战舰镜头的重复阴影级联。没有改配置、美术资产、攻击/概率/伤害/时序、重铸、全局分辨率、核心特效或保存策略。星系 30 建筑的渲染瓶颈仍在，不能宣称整游戏已达到 60 FPS。

## 环境与方法

- 唯一基线：`32991cc1187c9ebc100277ec8ea7a9d49538ffdc`，tree `700db97d215aa8110109ba8c14f47179f816f3a4`；直接 Git fetch。独立分支 `perf/whole-game-32991cc`，未推送。
- Linux / Godot `4.6.3.stable.official.7d41c59c4`；Xeon Platinum 8573C，系统可见 5 CPU，但 cgroup `cpu.max=400000 100000`，实际配额 **4 核**；`memory.max=17179869184`，**16 GiB**。
- 无 `/dev/dri`；Xorg dummy + OpenGL Compatibility，实际 renderer **llvmpipe (LLVM 19.1.7, 256 bits)**。图形数字是 CPU 软件渲染，不能冒充用户 Windows 真 GPU 数据；用户硬件未知，也没有因此停止 CPU 优化。
- 原配置上限 60 FPS，未发现低帧率 sleep/低功耗节流；HUD 每 0.5 秒读取 `Engine.get_frames_per_second()`。测量关闭上限/vsync，`low_processor_usage_mode=false`。截图 HUD 的 13→16 FPS 与图形帧耗时一致。
- 使用真实 `main.tscn` / `battlefield.gd` / `PresentedBattleGame`，未暂停。旧 Phase 9 / saved-game 探针只实例化旧 `main.gd`，会漏掉正式 3D 战舰。复用其包装计时方法，补充模块独立包装名，避免覆盖继承链。
- **合成夹具，不是用户存档**：重型战列舰，8 武器（四类各两件）+4 防御，模块 Lv150，船员 Lv103，强化 Lv30，三艘高 HP 固定目标，已有完整 30 建筑夹具。余额 `1e80`，每帧乘 `1.0000000001`，明确人为制造持续收入刷新；不代表用户实际余额或经济平衡。另测新档轻负载，不能用它代替高进度。
- 保留正式 `stat_cache_enabled=true`；隔离工程与用户目录，稳态测量关闭保存，保存 IO 单测。每页 15 帧预热+60 帧采样，窗口 **1373×883**、固定 1/60 游戏步，全部串行；图片读回在样本外。无插桩数字用于最终对照；嵌套函数计时仅归因，不相加。短样本 P99 等于 max，故下表使用 P95。

## 同条件结果

高余额 MAX 装备页，无图形，仅比较主循环 CPU，不能换算成实机 FPS：

| 主循环 ms | 基线 | 修复后 |
|---|---:|---:|
| 平均 | 196.10 | 28.25 |
| P95 | 200.75 | 35.16 |
| 最大 | 274.48 | 37.86 |

平均 CPU 减少 **85.6%**。该条件下，即使没有任何 GPU 渲染，旧报价已足以严重阻塞界面；这不是 llvmpipe 导致的结果。

六页固定步图形短测（同一高进度夹具，普通 ×1 报价）：

| 页面 | 总帧平均 ms 前→后 | 总帧 P95 ms 前→后 | 主循环 CPU 平均 ms 前→后 |
|---|---:|---:|---:|
| 战场 / 装备 | 79.31→63.79 | 87.72→71.01 | 11.58→6.88 |
| 装备强化 | 75.77→58.49 | 89.14→67.06 | 11.27→6.74 |
| AI 工厂 | 83.62→69.44 | 92.81→79.75 | 12.09→7.30 |
| 反应炉 | 86.66→73.56 | 96.62→88.36 | 12.05→7.70 |
| 星球 | 88.20→75.09 | 121.40→105.12 | 11.58→7.29 |
| 星系 30 建筑 | 350.19→334.87 | 365.91→347.30 | 12.09→7.53 |

前五页总帧平均改善约 **15–23%**，星系仅 **4.4%**。此前同条件短测也得到相近结果（战场 79.65→63.56 ms、星系 341.93→335.7 ms），不能把数毫秒波动解释成星系已解决。

真实自动 `_process(delta)` 另测每页 40 帧：普通战场总帧均值 **149.33→95.93 ms**，P95 **332.67→111.15 ms**；星系 **374.19→374.55 ms**，没有稳定收益。此组按真实墙钟推进，因此前后游戏时间/实体演化不同，只验证实际症状，不作逐步等价证明。早期使用的 `Performance.TIME_PROCESS` 是滞后采样，已从该组证据剔除；最终复用脚本改为直接测主循环。正常动态运行未出现脚本错误/警告洪泛。

## 热点证据与实现

1. **重复 MAX 报价**：插桩基线 10 帧，`refresh_affordability` 累计 1865 ms，120 次 `max_upgrade_amount_slot`，每帧 12 次逐级搜索；还重复累计显示费用和可负担费用。修复后同样 10 帧仅 **20 次搜索**，刷新累计 **223 ms**。`equipment_tab.gd` 在一次同步刷新中共享 `(类别,等级,升级数量)` 相同的报价；字典由该调用持有，资源/配置/换装/购买变化后下一次调用重新算，没有跨帧失效风险。`game.gd` 抽出原可负担检查，显示与按钮共用同一笔费用，逐级取整和实际购买路径保持原样。等级不同的模块不会合并；极端余额/全不同等级仍需线性搜索。
2. **保护层重复投影**：高负载无图形基线 `refresh_draw_layers` 平均约 **5.31 ms**，最终探针 **1.19 ms**。`enhancement_protection_status` 原来在组件、汇总和 HUD 再次计算相同容量/余额；现一次同步遍历同时形成组件与总额，HUD 在同一次刷新/绘制复用该结果。没有跨帧缓存，不延迟护盾、恢复、抵抗或倒计时。
3. **战舰重复阴影绘制**：相同重舰的 Viewport 可见绘制调用 **290→195**。正交俯视镜头使用单张完整范围的动态阴影图，保留阴影、4×MSAA、原 viewport 尺寸、全部模型/粒子/动画。隔离诊断中暂时关闭战舰/阴影只用于定位，最终代码没有这些关闭操作。前后截图检查未见舰体、炮塔、无人机或 UI 内容缺失。

## 分配、加载、卡顿与保存边界

- 六页稳态采样，每页节点增量 **0**、资源对象增量 **0**；Godot 静态内存约 **139.7–156.0 MiB**，单页增量约 **24–341 KiB**，前后接近。不是 RSS/GPU 总内存，也不是长时间无泄漏证明。未提供独立 GC 时间；不能把减少投影分配说成已修复 GC。
- 固定步每页的弹体/导弹队列峰值前后一致，最高 **20 / 10**；真实时间短测最高 **22 / 14**。没有改变队列、连发、伤害或攻击频率；这不是所有分支极端压力上限。
- 场景树仅一套战舰、星球设施、星系视口；静态战舰预览没有重复 3D viewport。隐藏星系停绘，星球设施是按可见页面请求的一次性更新，未发现每帧重复模型/材质重建。纹理 `get_image()` 在已缓存的轮廓/初始化路径；没有正常每帧 3D 读回。后台问题不是本次已证明的主因。
- 冷启动/首次显示仍有卡顿：初始首帧约 **802→869 ms**，首次星球页面显示 **266→299 ms**，未稳定改善；这些在预热外，包含渲染初始化/资源首用，不归为本次收益。切页同步调用多数 0.3–2.5 ms，强化页 **37.4→30.7 ms**。这不是 Windows 鼠标端到端延迟测量。
- 隔离 Linux 存储，8 次显式手动保存、43808 bytes：**1.936–2.624 ms**。本样本未出现保存尖峰，不能推断 Windows 磁盘最坏延迟。正式代码仍是手动+用户可调分钟定时，业务事件不即时保存；没有接入历史异步方案。
