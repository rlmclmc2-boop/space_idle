Implemented behavior:

- Resource balances use a canonical nine-digit main component plus one signed nine-digit residual. Legacy main-supported balances are rounded once on normalization; schema 2 persists both components. Operations use a fixed bounded cell set and decimal exponent metadata. Arbitrary mantissa fidelity and 1200-digit binary64 reconstruction are removed. The relative target is per representation/settlement, not an infinite accumulated-error guarantee.
- Ordinary price behavior and rounding remain. Large original-rule sums/refunds use bounded trailing terms and a checked omitted-tail budget; refunds never use MAX U. MAX encodes U upward and checks the final encoded `25U <= 28L + 24` certificate. Materials and levels remain checked int64.
- Existing asynchronous MAX wiring remains: pending/completion/confirmation, current-wallet fresh tickets, the same displayed fee, no wallet-change starvation, owner/config invalidation, sequential remaining funds, one aggregate native descriptor, and crew completion once. Income/drop/galaxy receipts preserve their source amounts.
- Actual ordinary/backup/portable/import paths validate bounded balances, high int64 materials and levels. The only hyperspace_state change is the approved preload/material validator substitution. Save parsing preserves integer tokens and duplicate/depth rejection. No global C.integer or general migration rewrite occurs.
- Native purchase preflight reuses only a validated, exact-content pack context: database inputs, schemas/configs and their bytes. Every candidate still passes data/state checks. Context changes require full pack validation; ordinary load/import paths retain full validation. Native rejection happens before effects. This removes duplicate full Game construction from each purchase, not from all save/load operations.

The user's further clarification (`Sentinel_4b69cd828ef48191a4cdb3f8599115eb`) asks whether this produces a shorter route to the same functional goal. Relative to main, Game's unbounded synchronous per-level MAX wallet loop is replaced by the bounded asynchronous query; ordinary prices and sums go through one price engine, and native prediction consumes the completed purchase plan instead of independently querying MAX/repricing. This is a numerical backend and scheduling replacement as well as adapter work. The fixed two-component balance removes arbitrary-tail work from this P2 candidate; it does not make main's already-small m/e representation simpler. Combat still uses the existing number module; no global number layer or gameplay subsystem has been retired.

The cost is substantial: seven new numerical/query scripts, 18 existing scripts adapted, and a net **2,002 added lines** (2,215 additions / 213 deletions). UI, crew, analysis and saves now share clearer price/value contracts, but fewer affected modules or lower overall coupling has **not** been demonstrated. Tickets, asynchronous lifecycle and storage validation add complexity. The demonstrated benefit is usable extreme MAX with bounded frame work and shared quoted fees; a measured overall speedup versus main, lower memory, faster ordinary purchases or faster saving has **not** been demonstrated. Purchase preflight reuse reduces a newly introduced P2 cost, not a measured main cost. The remaining save stall means this candidate should not be presented as a broadly faster or smaller implementation. No extra refactor is justified merely to improve these claims.
